# Goety witch cauldron integration

The feature lives in `com.huanghuang.rsintegration.feature.goety`. It registers
through `RSIIntegrationApi`, the [machine GUI API](MACHINE_GUI_API.md), and the
[storage API](STORAGE_API.md). Recursive material orders use the existing
`RSICraftConsumerApi`. No new cauldron Mixin is required.

When Goety is installed and the existing Goety integration config is enabled,
a held RS terminal opens a compact parchment notebook; ordinary interactions
and sneaking machine binding retain their normal behavior. Bound machines also
expose the notebook through RSI's remote machine GUI route. Selecting effects,
enhancements, and materials happens on separate pages. The server recommends
the smallest native-valid capacity, matches loaded Ingredient rules, selects
available equivalent catalysts, and checks permissions before extracting any
real items. Explicit item inputs remain exact; tag inputs remain interchangeable.
Bound networks can supply a named ladle without consuming it.

The parchment texture is generated by `scripts/GenerateGoetyNotebook.ps1` using
System.Drawing and a fixed random seed. It contains no downloaded artwork.
Goety, RS, Curios, and JEI remain external compile/test dependencies.

## Test commands

Use Java 17 and the upstream project's normal local dependencies. The Goety
test runtime additionally expects `libs/goety-2.5.56.4.jar` and
`libs/curios-forge-5.14.1+1.20.1.jar`. Test classes are in a separate source set;
normal `build` and `jarJar` do not include them.

```powershell
./gradlew.bat runGameTestServer -PgoetyGameTests
./gradlew.bat runClient -PgoetyUiSmoke
./gradlew.bat build verifyReleaseJar
```

For the client smoke, first create a disposable world named
`GoetyRSI-UI-Test` under `run/goety-ui/saves/`. The test changes blocks and
inventory in that world. It checks terminal entry, three-page navigation,
water exchange and resizing, then orders four sticks from logs stored in a real
RS network using a connected integrated-server player.

The 21 GameTests cover preview isolation, native brewing rules, remote opening,
registration lifecycle, water/bottles, material rollback, grouping, auto capacity,
real storage and named ladles, concurrent player actions, and offline refunds.
Expected completion markers are `NOTEBOOK_UI_PASS` and
`ONLINE_RECURSIVE_DELIVERY_PASS`.

## Verification limits

The implementation was compiled and tested in a focused ForgeGradle harness
against the supplied RSI 1.5.2.4 binary. All 21 GameTests passed, the client
completed both smoke markers, and assembled release JARs opened the menu on
Java 17 and 21 dedicated servers. The upstream full-source build is still
unverified in this environment: its Mixin plugin artifact and several local
optional-mod dependencies were unavailable. The opt-in upstream test wiring
above still needs a run in a fully provisioned upstream checkout.
