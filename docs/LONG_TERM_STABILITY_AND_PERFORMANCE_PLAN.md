## 1. 一页看懂这次准备做什么

### 1.1 一句话目标

**让复杂合成可以慢一点完成，但不要长时间拖住服务器；无论成功、失败还是中途退出，都要把物品和状态处理清楚。**

这不是“只让寰宇剑能合成”的方案，而是面向工作台、锻造台、熔炉、加工机器、祭坛、多方块、药水变换和其他特殊配方的长期方案。

### 1.2 优先级

| 顺序 | 优先保护什么 | 具体含义 |
|---|---|---|
| 第一 | 物品安全 | 不吞物、不重复产出、不误拿别人的物品、不清掉词缀 |
| 第二 | 服务器稳定 | 不让一次复杂预览或合成独占服务器很久 |
| 第三 | 合成正确 | 配方树、实际拿料、机器产出相互一致 |
| 第四 | 速度与资源占用 | 少重复计算，减少 CPU、内存和等待时间 |
| 第五 | 支持范围 | 在前四项满足后，再扩展更多特殊机器 |

**不能为了“合成更快”牺牲前面三项，也不能把“不支持”当成主要优化手段。**

### 1.3 准备怎么做

先记录哪里慢，再减少重复计算；然后把大任务拆成多次完成，最后处理复杂机器和中途异常。

不重写整个项目，不一次修改所有机器，不把“多开几个线程”当成解决办法。沿用现有的配方、机器和物品管理结构，逐步补齐公共能力。

### 1.4 本方案不承诺什么

- 不承诺所有整合包永远不掉 TPS；怪物、区块、其他 mod 和机器自身运转也会影响服务器。
- 不承诺所有配方瞬间算完；复杂请求可以排队、分段或明确告知暂时无法确定。
- 不承诺未知机器无需适配即可安全支持。
- 不用“测试全绿”代替真实整合包测试，也不用平均耗时掩盖偶发的大卡顿。

## 2. 当前情况：哪些已确认，哪些还不能下结论

### 2.1 已完成的基础

- 已修复并提交一轮无法破坏工具、词缀木剑及递归锻造链相关问题。
- 版本号保持 1.4.2。当前本地提交是 `9283a38`。
- 上一轮构建有 1342 项测试通过，并完成发布 jar 校验。这是正确性检查记录，不是性能成绩。
- 项目已有后台规划、队列、执行预算、物料账本和机器观察接口；本方案主要是改进和统一使用它们，不是全部从零建设。

### 2.2 已发现的风险

| 风险 | 用简单的话解释 | 目前证据 |
|---|---|---|
| 规划回到主线程执行 | 后台没算好，又让服务器停下来算一大段 | 当前代码有此路径；旧日志出现过 500ms typed 规划超时 |
| 限制没有覆盖准备工作 | 正式搜索有限制，但之前整理大量配方的工作可能没算进去 | 当前代码检查 |
| 同一份数据反复整理 | 重复找配方、扫描库存、解析物品属性 | 当前代码检查 |
| 外层有限时，内部仍可能很慢 | 开始一次操作后，不能立即暂停里面的第三方调用 | 当前调用结构 |
| 一次拿很多种材料 | 拿料、检查和失败返还可能集中在一次操作内 | 当前物料提交结构 |

### 2.3 不能误判的事情

- 旧日志中的 500ms 规划超时对应红羊毛，不是已经证明寰宇剑卡了 500ms。
- 绑定扫描的 949ms 是整个扫描任务的历时；代码已经分多次执行，不能说某一次服务器更新卡了 949ms。
- 配方目录后台构建用了几秒，不等于主线程一定停了几秒。
- 45 秒、23 秒的服务器落后记录，还没有当时的主线程采样证据，不能直接归罪于 RS Integration。
- 上次核对的游戏日志停在 2026-09-05 17:08:40，早于修复版部署。它不能证明新版是否已经改善性能。

详细代码证据保存在同目录 `SWORD_CHAIN_PERFORMANCE_AUDIT_2026-09-05.md`。

## 3. 必须守住的规则

### 3.1 不改变物品本身来“修好匹配”

例如你的木剑具有 Unbreakable、Damage、RepairCost 和 itemModifier。它们不能因为规划方便就被清掉。

- 允许的差异只按已经确认的规则处理，例如全新无法破坏工具的缺省 Damage 与 Damage:0。
- 损坏工具不能假装成全新工具。
- 配方要求部分属性，不代表退款时可以随便还一把同类工具。
- 机器是否继承附魔、词缀或其他状态，必须遵守该机器的真实规则，不能全部照搬锻造台。

### 3.2 算计划和动库存分开

可以让后台根据一份“库存照片”算怎么合成，但不能让后台随意修改正在运行的机器和库存。

真正拿料、投料、收取之前，还要确认照片没有过时；发生变化时重新校验，必要时重新规划或等待状态稳定。避免无休止从头重算，不新增固定重试次数来截断本来可以完成的路线。

### 3.3 不让优化绕过机器玩法

需要燃料、能量、时间、结构、维度或玩家条件的机器，仍要满足这些要求。不能为了省服务器开销，直接生成本应由机器生产的物品。

### 3.4 未确认的物品不能凭空返还

如果机器可能已经消耗原料，不能因为超时就把原料完整补回来。必须区分“没拿料”“已经拿料”“已经交给机器”“已经产出”。

无法确认时，保留记录、停止重复操作并提示处理，而不是冒着复制物品的风险自动退款。

### 3.5 每次修改都能检查、定位和退回

所有阶段单独提交、单独验收。没有通过物品安全检查的阶段，不进入日常整合包使用。

不删除本地化文件，不覆盖用户已有改动，不擅自换版本号，不把故障日志关闭来当作修复。

### 3.6 不靠硬截止换取性能

后续优化以减少重复计算和保存进度分次执行为方向，不新增“算够几步、超过几毫秒、候选太多就失败”的规则。耗时统计不参与决定请求是否终止。

已有的超时和防循环保护本轮不调整；用户主动取消、过时请求取消仍然有效。缓存可以限制留存量，但存不下时要照常计算，不能把存不下当成材料不足或配方不可达。

## 4. 希望玩家最终看到什么变化

以下是目标体验，不代表现在已经实现。

| 场景 | 目标表现 |
|---|---|
| 打开复杂配方树 | 可以显示“正在计算”，但其他玩家不需要一起等服务器恢复 |
| 连续点几次同一预览 | 只保留必要的最新请求，不堆一串重复计算 |
| 从木剑或石剑继续升级 | 继续使用实际库存工具，保留其合法属性 |
| 缺原料 | 显示经过确认的缺料，而不是把规划超时也显示成缺料 |
| 机器没有能量或输出堵住 | 显示具体等待原因，不反复重新计算整条链 |
| 多人同时合成 | 公平排队，不让一个超大订单长时间挤占所有人 |
| 玩家取消任务 | 未交给机器的材料可安全返还；已开工部分说明如何处理 |
| 玩家退出或机器卸载 | 暂停、停止新操作或进入恢复流程，不偷偷重复投料 |
| 真正发生异常 | 能看到卡在哪个阶段、哪个配方、哪台机器，以及是否持有材料 |

建议统一状态名称：排队中、计算中、待校验、待机器、待资源、加工中、收取中、恢复中、已完成、已取消、失败待处理。

“暂时没算完”“没找到受支持的配方”“机器条件不满足”“真的缺材料”必须分开显示。

## 5. 所有机器如何一起优化

### 5.1 公共部分只做一遍

把“查库存、找候选配方、理解物品属性、判断可达路线”尽量整理成一次请求共享的结果。配方树、最大合成数和实际计划不要各自重复做同样的事情。

可以理解成：先做好目录，找一本书时查目录，而不是每次把整个图书馆翻一遍。

但目录会过时。配方重载、库存变化、绑定变化后，应让相关旧结果失效。缓存必须限制数量和占用，不能越玩越大。

### 5.2 大任务分多次完成

必须在服务器线程处理的工作，应能记录进度、稍后继续，而不是每次开始就一直做完。但不能把所有请求都切成很小的片段，让玩家为普通操作长时间等待。

采用“快速路径优先、自适应让出、从进度继续”的原则：

- 普通短请求保留快速路径；可用准备缓存只省去重复准备，不证明剩余搜索很短。纯数据后台任务优先连续运行，不人为等待下一 tick。
- 服务器此前空闲不代表本次主线程长计算安全；不能凭历史 TPS 正常就允许复杂请求无限连续占用主线程。
- 只有观测到本次纯计算持续占用主线程，或服务器同时有其他重要任务时，才让出主线程。
- 让出是协作式调度，不是失败条件；不新增“超过多少毫秒/节点/候选就判定失败”的硬截止。
- 每个可让出的规划任务必须保存递归栈、候选游标、已完成材料分配和失败记忆，下一次从原位置继续，不能重新从根节点扫描。
- 分片批次应根据最近几次实际耗时动态调整：服务器空闲时增大批次，出现压力时暂时减小批次；不得固定成过小批次。
- 计算尚未完成时只能显示“计算中/继续计算”，不能显示“材料不足”；只有完整搜索结束后才报告缺料。
- 玩家主动取消、请求过时或发生异常时，释放排队状态，并保留已有材料账本和恢复流程。

重点是“继续上次进度”，不是“每次超时后从头再来”。所有玩家共享一个预算，并保证取消和恢复任务也能得到执行机会。 

限时是协作式的：一次很慢的第三方调用不能被安全地从中间切断。因此还要记录慢调用，减少重复调用，必要时暂停受影响机器的新任务。

#### 入口改动前的研究结论（2026-09-05；后续实施状态见下节）

| 已核对的落点 | 当前行为 | 后续取舍 |
|---|---|---|
| `AsyncPlanningCoordinator.execute`、`AsyncPurePlanningService.compute` | 纯规划在工作线程内连续计算，完成后通过服务器执行器交回结果；已有取消、同键请求合并及回交校验接口 | 保留后台连续计算，不把已经异步的工作拆成每 tick 一小段；不盲目增加线程数 |
| `GenericCraftPacket.tryBuildPlan` 中的 `PureDemandTreeInspector.inspect` | 路由检查发生在 `PLAN_REQUESTS.submit` 之前，其中有图准备工作；直接终端计划已有短路 | 优先审查能否在主线程捕获完整不可变数据后，将纯检查与后台规划放在同一个作业里；保留直接终端快速路径及原路由规则 |
| `AsyncPlanningCoordinator.execute` 的特殊回退，以及 `GenericCraftPacket` 的 typed 回退 | 某些后台失败/不兼容情况仍交回主线程同步处理 | 分别测量准备、回退计算和回交耗时，再缩小需要主线程的范围；不能一概禁用回退，否则特殊机器会失去支持 |
| `PureRecipePlanner.Search.solve` | 存在 Java 方法递归、局部候选循环、分支库存与回溯；目前没有可恢复的会话接口 | 不能通过抛出“让出”异常再重新调用 `resolve` 冒充续算。若证据需要，先建立完整显式搜索帧及回滚状态，保持旧求解器作等价参考 |
| `PlanningLookupCache.run` | 缓存绑定调用期间的 ThreadLocal，finally 释放 | 不为跨 tick 续算把 ThreadLocal 留在线程上。若未来引入会话，须设计任务拥有的数据和进入/退出作用域，核对顺序、失效、取消释放和内存 |
| `AsyncCraftManager.onServerTick` | 已轮转任务并在链调用之间检查预算；单个 `chain.tick` 仍可运行较长时间，完成回调也共享预算 | 不再加一层固定延迟队列；分清链自身耗时与回调排队耗时，防止后台早已算完却迟迟不给用户结果 |

研究优先级是“提交前同步准备 → 同步回退 → 回交延迟”，不是先重写整个求解器。下节记录已实施的有限范围，不能据此声称已经消除卡顿。

此前“完整搜索结束才能显示缺料”还需区分支持边界：当前 pure 结果已区分 FEASIBLE / INFEASIBLE / UNKNOWN，但受支持图内不可解不等于整个整合包绝对缺料。路由不支持、旧搜索保护触发、暂停和异常不得新增映射为材料不足。

#### 第四批实施：同一个后台任务完成路线检查和纯规划

- `GenericCraftPacket.tryBuildPlan`：符合后台候选条件、没有强制配方或材料锁的非直接完成请求，在主线程捕获值数据和路由策略后，直接提交组合任务。不再先同步展开路线，再提交后台，再在回交时重复同一次路线检查。
- `AsyncPurePlanningService.submitRouted/computeRouted`、`PlanRequestService.submitRouted`：复用现有协调器，在一个工作线程调用和缓存作用域里顺序完成检查及适用的纯规划；中间不交回主线程，不添加按 tick 暂停。结果包含快照、路由策略、检查结果以及可空的纯计划。
- 不兼容图仍返回原检查状态并进入原 typed 流程，不把“不适合纯规划”当缺料；主线程专用目标、强制配方和材料锁仍走原路径。发现不兼容的候选可能增加一次后台往返，这个延迟须实机测量，不承诺所有机器都更快。
- 回交沿用请求代次、快照及库存/绑定校验；同时比较路由节点配置和催化剂/不兼容集合。策略变化则丢弃旧路由和旧计划重新准备，不能复用旧判断。typed 入场排队继续传递有效路由结果。
- 合并键包含原规划键、路由值和库存遍历顺序，避免共享不同语义/顺序的任务。新版本不持有世界或机器对象到工作线程，不跨请求全局缓存可变物品。
- 此次只改 `tryBuildPlan` 这一入口；其他入口的路线检查、图捕获/绑定准备、typed 实际求解、机器执行和回交组装仍有同步部分。没有重写递归搜索，也没有实现主线程可续算。

新增观测通过已有性能摘要输出：`previewPrepare`、`queueWait`、`handoffWait`，格式均为次数/平均/最大微秒。
- `previewPrepare`：该入口从一次调用开始到路由阶段前的准备耗时；不含随后策略集合捕获、回交组装，也不覆盖提前返回的缓存命中/错误。一次请求可能重入，不能当作完整点击耗时。
- `queueWait`：协调器提交到工作线程实际开始；合并请求沿用原作业的提交时刻。
- `handoffWait`：工作计算结束并准备提交回调，到有效终态回调开始；取消/丢弃结果不累计到该指标。不含后续库存重验和响应构造。
- 原 `exec` 为后台作业实际执行耗时；本入口现在包含检查和适用的搜索。前后比较须注意范围变化，不能把移到后台的准备计时当成搜索退化。
- 所有新增计时仅观察，不触发超时、裁剪或等待。统计是累计值，不是每个请求的链路追踪，也不是实机 P95 或点击到计划延迟。

| `craftingTypedPreviewTimeoutMs` / `craftingResolveTimeoutMs` | 默认 500 / 2000ms；不变 | 涉及主线程同步求解，不能把放宽上限说成必然提速 |
| `craftingServerTickBudgetMs` | 保持 8ms | RSI 活跃执行链共享预算，不是所有规划的预算，也不能抢占内部单次调用 |
| `craftingCompletionCallbacksPerTick` | 保持 1 | 限制的是 `AsyncCraftManager` 执行链完成队列，不直接限制 `AsyncPlanningCoordinator` 的预览回交；先前把两者关联过于宽泛 |

排队宽限的依据是可复现调度场景，而非已测 TPS：32 个不同玩家同时入队、每 50ms 放行一个且任务自身耗时忽略时，1 秒宽限只能执行前 20 个，12 个尚未开算就过期；3 秒可执行全部 32 个。空队列同一时刻就可执行，不会为了宽限增加等待。真实低 TPS 或慢回调仍可能过期，不承诺 3 秒是最佳值。

必须纠正的表述：
- 历史日志中 45 秒和 23 秒服务器落后不证明是 RSI 导致，仍没有对应采样锁定调用。
- 最新 `latest.log/debug.log` 的修改时间仍为 **2026-09-05 17:08:40**，早于这些优化候选。不能说已验证新代码卡顿或改善。
- `debug.log` 在 **2026-09-05 13:58:23.415** 确有 `enigmaticlegacy:wool/red_wool` 的 typed 500ms 超时记录。这能证明当时该路径触发旧超时，不能证明整个剑链卡顿原因，也不能证明第四批候选仍如此。
- 后台配方目录构建几秒不等于主线程停几秒；缓存/索引工作次数减少不等于同百分比的 TPS 提升。
- “服务器空闲就可在主线程一直算完”不严谨：先前空闲不能预测接下来的长调用。本批没有据此放宽主线程预算。
- 外部 JEI/其他 mod 错误未修复，本批没有游戏新运行证据，不能确认其是否继续发生。

| 熔炉、耗时耗能机器 | 燃料、能量、加工时间、输出空间 | 等待有原因，避免反复启动 |
| 锻造、附魔、药水变换 | 实际输入决定实际产物 | 保存和验证状态变化，不用无属性展示物代替真实输出 |
| 祭坛、多方块、仪式 | 结构、环境、权限、机器占用 | 开工前检查，必要时重新确认，不每次全面扫描 |
| 催化剂、容器返还、多产物 | 哪些被消耗，哪些归还，哪些可以给下游 | 逐项记账，避免重复使用或遗漏 |
| 随机产物、实体交互、未知动态配方 | 结果不一定能提前确定 | 不承诺必得产物；取得真实结果后再继续下游 |

一个 mod 可能同时包含多类配方，不能只按 mod 名字决定全部行为。

## 6. 具体实施计划与通过条件

### 总安排

阶段 0 已有本地代码基线和本文档。用户已同意开始，目前已推进公共查询缓存、配方图准备复用、库存候选索引三批低风险优化；真实整合包性能基线及后续阶段仍按各自验收要求推进。

不提前承诺几天完成：先用真实测试确定工作量。每个阶段都要交付“改动说明、测试结果、剩余问题和可退回位置”，而不是一次攒出一个难以检查的大版本。

### 阶段 1：建立真实基线与安全记录

**目的：先知道哪里慢，并确定优化前后物品是否一致。**

计划工作：
- 在测试环境使用同一份存档副本、同一批物品和相同配方。
- 分别测不操作、仅打开预览、实际合成，区分其他 mod 的负载。
- 记录库存整理、计划准备、路线搜索、拿料、投料、观察、收取和恢复各阶段耗时。
- 记录配方 ID、机器类型、条目数、排队情况；日志限频，避免记录本身成为负担。
- 明确哪些机器已覆盖、哪些还未验证，不把“支持列表”当成测试完成列表。

交付：可复现的测试步骤、优化前数据、按证据排序的问题清单。

通过条件：至少能复现并区分一个主要慢点；能够核对关键测试的合成前后物品变化。没有在线证据时，不声称已经锁定全部卡顿根因。

### 阶段 2：先做低风险优化

**目的：少做重复工作，不改变合成结果。**

计划工作：
- 为配方和库存按物品 ID 建立查询目录。
- 同一请求中的物品属性解析、状态展开和规划准备尽量复用。
- 修复最大合成数探测等路径的重复准备。
- 为缓存设置容量限制、失效规则和释放时机。

交付：公共查询与缓存优化，明确哪些计算减少了，保留前后对比。

通过条件：已有关键回归全部通过；相同场景的材料选择和产物不变；重复扫描或准备次数确实下降；没有新增明显卡顿或持续内存增长。

### 阶段 3：让复杂规划不再长期占住主线程

**目的：预览复杂配方时，服务器仍能继续处理其他事情。**

计划工作：
- 将不依赖实时世界的路线检查和状态准备放到后台。
- 将确实需要访问机器的规划拆成可继续的步骤。
- 分别记录准备、搜索和整体请求耗时；需要分片时保存进度继续，不把新增的总耗时或次数阈值当成终止请求的理由。
- 合并重复预览、限制排队长度、取消过时请求。
- 超时显示未确定，不虚报缺料，不无条件启动更昂贵的同步重试。

交付：可排队、可取消、可继续的规划流程，以及明确的玩家提示。

通过条件：复杂请求可以跨多次处理完成；不会不断从头重算；多人请求不会长期挤占；较大但受支持的配方仍能成功，不能仅靠快速拒绝达到“性能改善”。

### 阶段 4：统一机器调度和等待方式

**目的：运行机器多了，也不把扫描、启动和收取集中在同一时刻。**

计划工作：
- 把机器准备、启动、观察、收取等 RSI 工作纳入共享预算。
- 对玩家和机器公平分配机会，同一台机器不能被两个任务同时抢用。
- 按机器特点调整查询频率；无能量、结构无效和输出堵塞采用不同等待原因。
- 对反复异常的配方或机器暂停新任务，保留现有物品恢复流程。
- 对具体慢调用报警，但不关闭其他正常机器或整个功能。

交付：统一调度机制及首批代表性机器适配。

通过条件：多个任务能持续前进；等待不会忙循环；没有因少查询而漏掉产物或重复开工；取消和恢复请求不会一直被新任务挤占。

### 阶段 5：加强物料交接和异常恢复

**目的：分多次执行后，仍然知道每一份材料在哪里。此阶段风险最高，应拆成更小提交。**

计划工作：
- 先合并等价拿料和重复校验，再根据阶段 1 的证据决定哪些事务必须拆开。
- 对“预留、拿到、投入、消耗、产出、归还”建立明确记录。
- 处理其他玩家中途修改库存、机器被拆、区块卸载、输出塞满和网络失联。
- 确认同一个完成通知、退款请求或收取动作重复到达时，不会重复执行。
- 若引入跨重启恢复记录，必须规定保存格式、升级兼容和无法确定时的处理办法；未完成前不得宣传崩溃后必定自动恢复。

交付：异常恢复流程、故障模拟测试和人工处理说明。

通过条件：在每个交接点模拟取消或失败，均不重复生成物品、不拿走无关物品；不能确定归属时，状态清楚且不会自动再次扣料或凭空退款。

### 阶段 6：扩大机器覆盖并进行长时间验证

**目的：确认公共优化对普通机器和特殊机器都能长期工作。**

迁移顺序：普通工作台和固定加工 → 熔炉和耗时机器 → 状态变换 → 祭坛、多方块 → 随机与其他特殊配方。

每类先选代表性机器通过，再扩大范围。每个适配器都要记录投料、开工、完成、失败和退款的证据来源。

交付：机器兼容矩阵、长时间运行结果、已知限制、候选发布包。

通过条件：没有未解释的物品异常；任务和缓存不会不断累积；旧任务结束后资源能释放；核心配方链和多人场景均通过。

## 7. 测试与验收计划

### 7.1 正确性测试：结果有没有变错

| 测试组 | 必测内容 |
|---|---|
| 原有问题 | 原词缀木剑、石剑起步的完整升级链；树显示和实际执行一致 |
| 属性边界 | Unbreakable 类型差异、Damage 缺省/0/非 0、词缀、附魔、RepairCost，以及已适配的特殊状态 |
| 普通配方 | 无属性材料、标签材料、严格属性配方不能因优化被放宽 |
| 物料角色 | 消耗品、催化剂、可重复使用工具、容器返还不混淆 |
| 数量 | 单次、多次、缺一件、库存刚好够、大数量，不溢出或重复计数 |
| 复杂路线 | 多候选、相互转换、循环配方、共享前置材料，不无限递归 |
| 真实产物 | 动态属性、多个产物、概率产物、展示占位物不被误当成真实库存 |

### 7.2 异常测试：最容易吞物的情况

分别在“拿料前、拿料后、投料后、加工中、收取中、退款中”检查：

- 玩家取消、退出、再次请求同一任务。
- 另一个玩家拿走材料或占用机器。
- 输出空间满、存储断开、机器被拆或替换。
- 区块卸载、配方重载、机器条件改变。
- 某个第三方调用报错、返回部分成功或没有明确结果。
- 正常停服后重启；若实现崩溃恢复，再在存档副本中单独测试异常退出。

物品核对不能只比总件数，要核对种类、数量、属性和归属。配方正常消耗、容器返还及合法产出也要记入对账。

### 7.3 性能测试：是否真的减少卡顿

先记录优化前结果，再用相同环境记录优化后结果。首次加载与重复使用分别统计；不能拿“优化前首次加载”去比较“优化后缓存已热”。

拟定测试档位，实际规模在阶段 1 根据测试机容量调整：

- 库存：小库存、约 1000 种、约 10000 种物品条目。
- 状态：少量和大量同物品不同 NBT 的工具。
- 请求：1 人、4 人、8 人的等效并发请求。
- 机器：少量运行、多机器并行、大量任务等待能量或输出空间。
- 配方：固定配方、完整剑链、多分支链、无法完成的链、最大合成数探测。

人工测试与程序模拟结果分开标注，模拟并发不能冒充真实多人整合包测试。

### 7.4 看哪些指标

| 指标 | 简单解释 | 想确认什么 |
|---|---|---|
| 主线程单次连续耗时 | 一次让服务器等了多久 | 是否仍有明显长时间独占 |
| 平均、较慢一批、最慢一次 | 不只看多数时候快不快 | 是否隐藏偶发大卡顿 |
| 排队时间、成功率 | 玩家实际等多久，能否完成 | 不能靠拒绝复杂任务换取好看的耗时 |
| 点击到首个有效反馈、点击到完整可执行计划 | 预览是否只是显示得快，实际却一直等 | 与同一存档、同一库存下的候选前版本比较 |
| 后台完成到结果回交的延迟 | 算完后是否仍被队列拖住 | 区分计算慢与调度等待，不人为增加空闲 tick |
| 让出次数、续算进度、短链延迟 | 分时是否反而拖慢操作 | 短请求不强制跨 tick，长请求不重复从根搜索；不新增超时失败指标 |
| 重复扫描、重复规划次数 | 同一件事算了几遍 | 公共优化是否有效 |
| 缓存、待处理任务、内存趋势 | 玩久之后是否越来越多 | 是否有积压或泄漏 |
| 机器查询次数与完成延迟 | 查得少了是否漏事 | 降低开销与及时响应是否平衡 |
| 物品异常和未知状态 | 是否安全 | 是发布门槛，不是可忽略的性能代价 |

阶段 1 后再制定有依据的具体性能目标。现在不保证一个固定毫秒数，也不要求所有机器和电脑使用同一套参数。

### 7.5 长时间观察

建议候选版在存档副本中完成至少两小时的混合运行测试，包含持续合成、取消、空闲、多机器等待和任务清空后的观察；高风险恢复改动还需单独延长验证。

两小时只是建议的第一轮检查，不是长期稳定保证。还应记录多次启动、长时间空闲及重载后的表现。

## 8. 发布、备份和退回办法

### 8.1 不直接拿日常存档试高风险改动

代码提交是代码备份，不是存档或物品备份。涉及物料恢复和保存格式时，必须有独立存档副本。

建议发布顺序：自动测试 → 存档副本实测 → 候选版少量场景验证 → 日常整合包。

### 8.2 每次部署记录这些信息

- Git 提交号、版本号、构建时间和 jar 文件校验值。
- 使用的整合包、配置和测试场景。
- 旧 jar 的备份位置，以及适用时的配置、存档和任务记录备份。
- 本次改变了哪些机器行为，哪些机器仍走旧路径。

当前版本号仍为 1.4.2。将来是否调整由用户决定；如果继续使用相同版本号，也必须通过提交号与校验值区分不同构建，不能仅看文件名。

### 8.3 出问题后如何退回

1. 先保存日志和任务状态，停止受影响机器的新请求，不直接清空账本。
2. 若服务器仍可响应，尽量完成安全结算；无法确认的操作保留证据，不强行退款。
3. 停服后备份当前状态，再判断能否退回旧 jar。
4. 只有确认保存格式兼容时，才能把换回旧 jar 当成完整退回。
5. 如果格式不兼容或物品状态已经改变，按经验证的迁移/恢复办法处理；不能随意用旧存档覆盖日常进度。

**退回代码不等于撤销机器已经消耗的材料。**这是本方案必须单独验证的事情。

## 9. 长期维护安排

### 9.1 每次增加或更新机器支持

填写一张简短的兼容记录：

- 配方从哪里发现，真实输入输出是什么。
- 是否继承或改变物品属性，是否存在特殊状态。
- 是否需要能量、环境、结构、权限或占用锁。
- 如何确定机器已经开工，如何确定产物属于本次任务。
- 哪些情况下能取消和返还，哪些情况下不能。
- 是否经过成功、缺料、中途取消、输出堵塞和拆机器测试。

没有确认上述事项的适配，不默认标为“完整支持”。

### 9.2 每次修改公共规划或物品匹配

必须跑跨机器回归，不只测刚修的那台机器。尤其检查普通无属性材料、严格属性配方、催化剂和随机产物，避免“修好木剑，弄坏祭坛”。

### 9.3 每次升级整合包或第三方 mod

对版本变化涉及的机器做小范围复测，检查配方类型、槽位、状态、产物和完成判定是否改变。不假定旧反射字段、旧物品 ID 或旧规则永久有效。

### 9.4 日志和诊断

默认日志保持简洁：记录状态变化、超时、慢操作和失败原因；同类重复错误限频并给出次数，不每次查询都打印。

深入排查时使用已有 `/rsi_debug perf` 和 `/rsi_debug dump chain`，后续再补齐必要阶段指标。性能数据要带时间窗口，不能把启动时的历史最大值当成本次合成耗时。

不默认上传玩家背包、完整 NBT、存档或日志；需要分享时先按排查目的截取和脱敏。是否安装额外性能分析工具、启动实测或长时间运行，另行确认。

### 9.5 参数保持克制

优先保留少量可解释的设置：工作预算、排队上限、并发上限、诊断开关。安全限制不应随意关闭。

增加工作线程、扩大单次批量、延长同步超时，都不是默认优化方向。调整应有前后数据，并记录复杂配方成功率是否受影响。

## 10. 风险、取舍和暂时不做的事情

| 风险或取舍 | 应对原则 |
|---|---|
| 缓存过时导致拿错材料 | 执行前重验；限制缓存生命周期和容量 |
| 分段后整体完成时间略长 | 优先保证其他玩家能正常活动，同时监测任务是否公平前进 |
| 降低查询频率使产物晚收一点 | 按机器特点设置观察方式，检查堵塞和完成延迟 |
| 预算太低导致复杂配方总失败 | 允许保存进度继续，不用不断重来代替限时 |
| 第三方机器的一次调用很慢 | 记录具体位置，限制重复调用；不能强行杀线程 |
| 第三方机器自己就很耗资源 | 区分它的原生负载和 RSI 负载，不承诺公共优化能解决全部问题 |
| 特殊能力不能只靠 NBT 表达 | 专门适配或保守地表示未知，不猜测真实状态 |
| 崩溃后无法确定是否已经消耗 | 保留不确定状态，人工核对优先于凭空返还 |
| 优化分支越来越多、维护变难 | 先改公共层，机器差异集中到适配接口，逐步淘汰重复路径 |

暂时不做：重写整个项目、一次改全部机器、取消机器真实加工过程、把所有世界操作放后台、无限缓存、无限重试、强制加载区块来维持任务、关闭 watchdog、未经用户确认替换整合包文件。

## 12. 开发人员附录

本节供实现时定位，使用者不必先理解这些类名。以下是拟议职责划分，不是已实施改动。

| 现有组件 | 后续主要工作 |
|---|---|
| RecipeIndex / RecipeCatalog 构建流程 | 建立可复用配方索引，按配方更新失效 |
| ModRecipeHandler | 声明真实输入、产物、状态变化和支持边界 |
| IngredientMatcher | 统一配方语义，保留严格与部分匹配差异 |
| ImmutableRecipeGraphProjector | 减少全图扫描，准备结果请求内复用 |
| PureRecipePlanner / PureDemandTreeInspector | 共用状态规则，减少重复准备；分片时保存进度，不新增硬截止来截断递归 |
| PlanningSnapshot / AsyncPlanningCoordinator | 有界后台任务、过时请求取消、执行前有效性校验 |
| CandidateEngine / CraftingResolver | 库存分桶，减少重复发现；必要同步搜索可续跑 |
| AsyncCraftManager / ConcurrentNodeExecutor | 公平预算、有限观察、机器互斥及恢复优先级 |
| IBatchDelegate / 各机器适配器 | 真实开工、完成、产物和失败判定，不靠通用猜测覆盖一切 |
| ExtractionLedger / StorageSettlementLedger | 实际资源身份、分阶段交接、重复操作防护及恢复 |
| PerformanceMonitor | 分阶段耗时、排队、重复工作、慢机器及有界诊断 |

实现约束：
- 配方匹配宽松不等于物品归属宽松；不得全局替换严格的归属核对。
- 后台只使用已确认可安全读取的数据；任意 mod 回调不能因为名字叫“检查”就视为线程安全。
- 缓存键须涵盖影响结果的状态；不对活的 ItemStack/capability 做无边界跨请求缓存。
- 物品、流体、能量和环境条件分别处理，不用物品数量冒充所有资源。
- 日志状态、错误分类与实际流程一致；超时、未知、不支持、缺料和等待不能合并为一个失败分支。
- 不把巨型文件重构、格式化和无关功能混进性能补丁；先让提交范围可审查。

最终判断标准：**同样的配方和真实机器，物品结果不变；服务器等待更短、负载更平稳；异常时有明确状态，后续维护者能够定位和处理。**
